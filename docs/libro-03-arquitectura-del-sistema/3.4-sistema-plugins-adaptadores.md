# 3.4 — Sistema de Plugins y Adaptadores

> **Estado:** Aprobado (CTO por delegación D22, 2026-07-18) · **Prioridad:** P1 · **Responsable:** Opus

*Convención † (1.1 §4): desarrollo del arquitecto exigible con la aprobación; no es texto de actas del CEO.*

## Resumen ejecutivo

Define el contrato que materializa la Evolución Permanente (D14, ADR-0004): **cualquier tecnología se conecta a AURA como plugin sin tocar el núcleo** (3.2). Especifica el manifiesto de capacidades, el ciclo de vida (registro → sandbox → activación → actualización → retiro), el aislamiento y los permisos, la **seguridad de la cadena de suministro** (firmas, verificación), el versionado con la política de deprecación del ADR-0004, el descubrimiento de capacidades y la guía para incorporar tecnología nueva. Es el mecanismo que hace de AURA un sistema vivo. No lista plugins concretos (eso es el Libro VI); define el contrato.

## Objetivo

Que agregar un proveedor de IA, un dispositivo, un sistema o una modalidad sea **conectar un plugin conforme a contrato**, nunca modificar el núcleo — garantizando que ningún plugin comprometa la seguridad, la privacidad ni la estabilidad del sistema.

## 1. Contrato de plugin y manifiesto de capacidades

Todo plugin declara un **manifiesto**: `plugin_id`, `version` (SemVer), `capabilities` (qué expone: p. ej. `home.switch`, `llm.chat`, `system.exec`), `events` (qué tipos consume/emite, contratos de 3.3), `permissions_required` (qué acciones D4 puede solicitar), `data_scope` (qué datos toca; sujeto a ADR-0001), `dependencies` y `signature` (§4). El núcleo solo conoce el manifiesto y los contratos; nunca la implementación (P-ARQ-3).

## 2. Ciclo de vida

`registrado → verificado → activo → (actualización) → retirado`. Transiciones:

- **Registro:** se valida el manifiesto contra el schema registry (3.3) y se verifica la firma (§4).
- **Verificado → activo:** el plugin se activa dentro de su sandbox (§3) con los permisos mínimos que declaró (least privilege).
- **Actualización:** nueva versión conforme a la política de deprecación (regla 11 ADR-0004: máximo 2 versiones mayores vivas; ventana con término).
- **Retiro:** un plugin retirado libera sus recursos y sus capacidades desaparecen del descubrimiento (§5); nada en el núcleo se rompe (P-ARQ-3).

## 3. Aislamiento, sandboxing y permisos

- **Sandbox:** cada plugin corre aislado; no accede a memoria, credenciales ni a otros plugins salvo por contrato explícito. El grado de aislamiento (proceso, contenedor) es decisión de 3.6, pero el **contrato de aislamiento** se fija aquí.
- **Permisos por capacidad (least privilege):** un plugin solo puede solicitar acciones dentro de los `permissions_required` que declaró; el Gestor de Permisos/HITL (5.3) evalúa cada acción contra las listas D4 **independientemente** de lo que el plugin pida. Un plugin **nunca** ejecuta directo: emite una solicitud de acción por el bus y espera autorización (3.2 §5, 3.3 §4).
- **Frontera de datos:** el `data_scope` de un plugin se somete al ADR-0001; un plugin que envía datos a la nube pasa por minimización (regla 5).

## 4. Seguridad de la cadena de suministro

- **Firma obligatoria:** todo plugin se instala solo si su firma verifica contra una clave de confianza local; un plugin sin firma válida no pasa de `registrado`.
- **SBOM:** el manifiesto declara sus dependencias (software bill of materials) para trazar vulnerabilidades.
- **Sin auto-actualización silenciosa:** una actualización es una transición de ciclo de vida verificada (§2), no un proceso opaco. Esto cierra el vector de cadena de suministro que el modelo de amenazas (5.1) tratará en detalle.

## 5. Descubrimiento de capacidades

El **Registro de Plugins** (contenedor del 3.2) mantiene el catálogo vivo de capacidades activas. El orquestador (4.2) y los agentes (4.3) descubren qué pueden hacer consultando el registro por capacidad, no por plugin concreto — así una tarea "encender luz" se resuelve con cualquier plugin que exponga `home.switch`, sustituible (P-ARQ-4).

## 6. Guía: incorporar tecnología sin tocar el núcleo

Checklist para un plugin nuevo: (1) declarar manifiesto; (2) mapear sus operaciones a los contratos de evento (3.3); (3) declarar `permissions_required` y `data_scope`; (4) firmar; (5) registrar. Ninguno de esos pasos modifica el núcleo — es la prueba operativa de la Evolución Permanente. El catálogo concreto de adaptadores del MVP (HA, sistema, avatar, notificaciones) se especifica en el Libro VI sobre este contrato.

### Evaluación por las cinco preguntas (D21)

(1) Escala 10 años: tecnologías futuras entran como plugins. (2) Reduce dependencia: capacidades sustituibles por descubrimiento. (3) Sustituir sin rediseñar: es el objeto del capítulo. (4) Equipo pequeño: contrato único, no N integraciones a medida. (5) Sistema vivo: la definición misma de la Evolución Permanente. Sin respuesta negativa → sin Alerta.

## Riesgos

- **Plugin malicioso o comprometido:** mitigación: firma (§4), sandbox (§3), least privilege y HITL sobre toda acción (5.3); el modelo de amenazas lo profundiza en 5.2.
- **Fuga de datos por un plugin:** mitigación: `data_scope` + ADR-0001 + minimización; auditable (P-ARQ-7).
- **Proliferación de plugins inmantenible:** mitigación: cada plugin defiende su existencia (regla 13 ADR-0004); retiro limpio (§2).
