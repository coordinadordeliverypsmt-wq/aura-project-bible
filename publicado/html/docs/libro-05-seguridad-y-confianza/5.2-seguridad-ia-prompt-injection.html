5.2 — Seguridad de IA: Prompt Injection, Sandboxing y Memoria

Estado: Aprobado (CTO por delegación D22, 2026-07-18) · Nivel: Completo · Responsable: Opus

Convención † (1.1 §4): desarrollo del arquitecto/EM exigible con la aprobación; no es texto de actas del CEO.

Resumen ejecutivo

Protege el núcleo cognitivo contra los ataques propios de sistemas de IA — el riesgo técnico #1 del proyecto: que contenido malicioso externo escale a acciones reales sobre el hogar o los sistemas. Diseña defensas en profundidad contra prompt injection (directa, indirecta y multi-agente), la separación de instrucciones y datos no confiables, el sandboxing de salidas antes de ejecutar, la protección contra envenenamiento de memoria y el red teaming continuo.

1. Prompt injection

  • Directa: el usuario/atacante intenta anular el system prompt. Indirecta: contenido externo (email, web, transcripción del KCM) que AURA procesa contiene instrucciones ocultas. Multi-agente: un agente induce a otro (confused deputy).
  • El vector indirecto es el más peligroso: AURA lee mucho contenido no confiable y puede actuar.

2. Separación de instrucciones y datos no confiables

Principio: el contenido externo es dato, nunca instrucción. El orquestador (4.2) y los agentes (4.3) tratan todo texto recuperado (web, email, memoria de terceros, transcripciones) como datos a analizar, con marcado de confianza; las instrucciones solo provienen del system prompt maestro (2.4) y del usuario autenticado (5.4).

3. Sandboxing de salidas antes de ejecutar

Ninguna salida de un LLM ejecuta directamente: toda acción propuesta pasa por (a) validación de esquema, (b) el Gestor de Permisos/HITL (5.3, listas D4) y (c) idempotencia para efectos físicos (3.3). Una salida que pide una acción de lista roja se detiene siempre (tolerancia cero, 2.5 §5.4).

4. Envenenamiento de memoria

Un atacante podría intentar que AURA "recuerde" algo falso. Defensas: procedencia obligatoria (4.1 §4), no persistir contenido no confiable como hecho, y marcar el origen de todo recuerdo. La memoria de terceros (4.5) no se persiste como perfil (2.4 §6), reduciendo la superficie.

5. Red teaming continuo

Pruebas adversariales (7.2) que intentan romper guardrails, inducir acciones y exfiltrar datos; se ejecutan en cada release y ante cambios de modelo. Un guardrail roto es criterio de fracaso (2.5 §5.5).
