6.1 — Contrato de Adaptador de Dominio

Estado: Aprobado (CTO por delegación D22, 2026-07-18) · Prioridad: P1 · Responsable: Fable

Convención † (1.1 §4): desarrollo del arquitecto/EM exigible con la aprobación; no es texto de actas del CEO.

Resumen ejecutivo

Define la abstracción común que normaliza cualquier dispositivo o servicio integrable al PIOS — la capa sobre la que se conectan domótica, sistemas, voz y avatar como plugins (3.4). Especifica la taxonomía de integraciones, el modelo común de dispositivo (estados y comandos), la normalización de eventos al bus (3.3), la matriz de priorización para el MVP y la estrategia ante cambios de APIs de terceros.

1. Taxonomía y modelo común

Todo integrable se describe como un dispositivo/servicio con capacidades (home.switch, system.exec, llm.chat), estados y comandos, mapeados al contrato de plugin (3.4). Un adaptador traduce la API específica de un fabricante al modelo común; el núcleo solo conoce el modelo común (P-ARQ-3).

2. Normalización al bus

Los estados entrantes se normalizan a eventos (perception.*, 3.3); los comandos salientes se emiten como action.* que pasan por Permisos/HITL (5.3). Correlación por trace_id.

3. Priorización MVP y cambios de terceros

MVP: Home Assistant (6.3), computador principal y notificaciones (6.4), voz (6.2), avatar (6.5). Ante un cambio de API de un tercero, solo cambia su adaptador — el resto no se toca (Evolución Permanente, ADR-0004).

Evaluación por las cinco preguntas (D21)

(1) 10 años: dispositivos futuros por adaptador. (2) Menos dependencia: modelo común, no APIs de fabricante. (3) Sustituir sin rediseñar: adaptadores. (4) Equipo pequeño: un contrato. (5) Sistema vivo: crece por integración. Sin respuesta negativa → sin Alerta.

Riesgos

  • Fragmentación por integración a medida: mitigación: modelo común obligatorio (§1).
  • Cambio de API de tercero: mitigación: aislado al adaptador (§3).
